# 親共有配置への移行

3.0.0の簡素化したロール構成は維持し、設定を非Gitの親へ集約します。Docker DesktopまたはローカルDocker Engineを起動し、更新した配布元リポジトリから実行してください。ホストのPythonは不要です。

## 旧親環境から更新する

旧Guildの親をそのまま導入先に指定します。子リポジトリへの導入は不要です。旧キューなどを使用中のタスクやランタイムは終了してから移行します。インストーラー自体はプロセスを停止しません。

~~~bash
./scripts/install.sh --target /Users/nir-nmttg/Projects/achromono/asked-root --dry-run
./scripts/install.sh --target /Users/nir-nmttg/Projects/achromono/asked-root
~~~

旧v2の配布物を検出すると自動移行します。`--major-upgrade`を付けても同じ動作です。旧`--legacy-root`による親から子への移設は廃止しました。Gitルートそのものを`--target`に指定すると拒否します。

`archive_paths`と`legacy_actions`が自動整理対象、`preserved_legacy_files`が保持対象です。旧v2にはファイル単位のマニフェストがないため、[既知の旧配布ハッシュ](../scripts/legacy-v2-files.json)と一致するファイルだけを親の`.agent-guild-orchestra-archives/v2-to-v3-.../`へ退避して置換・削除します。カタログはこのリポジトリのv2.0〜v2.4配布履歴を基にしています。AGENTS.mdは管理ブロックだけを比較し、利用者が追加したブロック外の文を保持します。hooks.jsonは既知の旧Guildコマンドだけを除き、第三者コマンドを保持します。

変更済みの旧ロール・Skill、未知のファイル、独自設定、第三者Skillは削除しません。マニフェストのないSQLite等の可変状態も所有権を確定できないので自動削除しません。これらはv3から読みませんが、保持された旧名前付きエージェントやフックなどはCodexから見える可能性があります。一覧を確認し、必要な独自変更を移した後に利用者が整理してください。新配布先に変更済みの旧ファイルが重なる場合は、全書き込み前に停止します。

既存独自`.codex/config.toml`はユーザー管理の設定としてそのまま保持されます。`next_steps`の新設定と手動で統合し、旧ロール指定・フック・読み取り専用などの権限設定も確認してください。新設定の単純追記ではTOMLテーブルが重複することがあるため、既存テーブルを編集します。Rootの推論レベルは配布物では固定しません。

## 子へ導入したv3から戻す

まず同じコマンドで親に新設定を導入し、[親起動の確認](parent-layout.md)を行います。この段階では子の旧v3ファイルも含め、各子のファイル、index、Git設定は一切変わりません。

子の旧配置を退役させる場合だけ、対象を一つ明示して次を実行します。これは通常の導入・更新とは独立した、子ファイルの整理操作です。

~~~bash
bash scripts/cleanup-child.sh \
  --target /Users/nir-nmttg/Projects/achromono/asked-root \
  --child /Users/nir-nmttg/Projects/achromono/asked-root/repositories/asked_backend \
  --dry-run
~~~

`actions`を確認後、同じコマンドの`--dry-run`を外します。必要な子ごとに実行してください。再帰的な一括整理は行いません。

- 親のスキーマ2のマニフェストと、子のスキーマ1 / v3.0.0のマニフェストを必須にします。子は`repositories/`内の明示された実Gitルートでなければなりません。
- 子マニフェストのハッシュと一致し、Git indexに載っていない配布ファイルだけを退避して削除します。AGENTS.mdは管理ブロックだけを除き、ブロック外の文を残します。
- 変更済みファイル、Gitで追跡・ステージされたファイル、ユーザー管理の設定、第三者Skillを保持します。保持対象があれば元のマニフェストも保持し、残る競合を報告します。
- `.git/info/exclude`などGitメタデータは整理対象にしません。Git index・設定・除外ルールを変更せず、以前の除外設定も自動では戻しません。
- 退避先は親の`.agent-guild-orchestra-archives/child-v3-to-parent-.../child/`です。マニフェストがない場合は所有権を推測せず停止するので、利用者が履歴と差分を確認します。

Dockerはこの明示された子だけを例外的に書き込み可能にし、`.git`、リンクされたワークツリーの外部Gitメタデータ、他の子は読み取り専用にします。通常の導入・更新では子全体が読み取り専用です。

## 失敗時の復元

処理中の例外やCtrl-Cでは、変更したファイルをトランザクションバックアップから自動復元します。元と同一のファイルは触らず、必要なファイルは元の権限でアトミック置換します。一件の復元に失敗しても他のファイルの復元を試み、全ての復元が成功した場合だけバックアップと途中のアーカイブを取り除きます。対象外の独自ファイルと子Gitメタデータには触れません。

復元にも失敗した場合は、親の`.agent-guild-orchestra-recovery/transaction-.../`を残して標準エラー出力へ場所を報告します。子v3整理のバックアップも親に置くため、Dockerコンテナ削除後も残ります。`recovery.json`の`target`、対象パス、元の存在状態、ディレクトリ権限と、同じディレクトリ内のバックアップを確認してください。対象と現在の差分を照合し、権限や容量の問題を解消してから必要なファイルだけを戻します。元々存在しなかったファイルの一覧も含まれるため、一括コピーや自動再実行による復旧は行いません。復旧と確認を終えるまでバックアップを削除しないでください。

これは処理単位の復旧用バックアップであり、常駐ランタイムや自動リプレイ機構ではありません。強制終了、Dockerデーモン停止、電源断をまたぐ完全なトランザクションは保証しません。更新中は同じ管理ファイルを他のタスクで編集しないでください。

成功後に戻す場合、archive.jsonの対象一覧と現状の差分を先に確認してください。アーカイブを親や子へ一括上書きすると、その後のユーザー変更を失うため行わないでください。v2アーカイブは旧ファイルの退避であり、新配布ファイルを含む全ワークスペースのバックアップではありません。子v3の退避はメタデータの`child`と照合し、戻すファイルだけを選んで復元します。

## 以後の更新

~~~bash
./scripts/sync.sh --target /Users/nir-nmttg/Projects/achromono/asked-root --dry-run
./scripts/sync.sh --target /Users/nir-nmttg/Projects/achromono/asked-root
~~~

親マニフェストを基準に更新します。配布元と導入先の双方で変更されたファイルは手動で統合し、AGENTS.mdのブロック外や既存権限、ユーザー管理の設定は保持します。権限だけが配布時の値と異なる管理ファイルもローカル変更として扱い、更新時は衝突として停止、パッケージ除外時は保持します。旧版の配布権限を確定できないファイルも保守的に保持します。既存の子設定は`child_overrides`に表示されます。親の`AGENTS.override.md`がある場合もAGENTS.mdより優先されるため、[設定継承の注意](parent-layout.md)を確認してください。
