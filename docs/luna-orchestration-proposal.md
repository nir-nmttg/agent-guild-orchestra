本文の委譲・返却トークン数と算例も当時の設計記録です。現在の分量目安は[引き継ぎと結果](orchestration-runtime.md#codex標準の引き継ぎと結果)を参照してください。

推奨は、AstraのGuildmasterが直接統括する一層の構成を維持し、Luna Maxの役割を調査・実装・受け入れ検証・通常レビューに分けることです。サブエージェント枠はまず8を候補とし、通常の同時稼働は2〜4体、独立した仕事が十分ある場合だけ5〜8体に増やします。8は実測済みの最適値ではなく、3・4・8を比較するための初期候補です。

ユーザーの固定条件は、すべてのLunaを`gpt-5.6-luna` / `max`にすることです。Rootの推論レベルは従来どおりユーザーの選択を尊重します。

## 検討開始時の状態と改善対象

- [配布設定](../template/.codex/config.toml)と導入済みの親設定は`max_concurrent_threads_per_session = 3`。これはLuna専用枠ではなく、メインを除くサブエージェント全体の枠です。Inquisitorも消費します。[公式仕様](https://learn.chatgpt.com/docs/config-file/config-reference)
- [運用規則](../template/AGENTS.md)にも「独立調査は通常1体、最大3体」があります。設定値だけを増やしても分担方針は変わりません。
- Scholarはコード探索・資料調査・比較・反証、Adventurerは実装と局所検証を担当します。通常の独立した受け入れ検証と差分レビューには専用のLuna役がありません。
- Rootと全カスタムエージェントで、コンテキスト100万・自動コンパクション90万を共通指定しています。大きい窓があることと、毎回その量を使うことは別です。まず渡す情報と読み込む範囲を減らします。
- 既存の[モデル比較](model-selection-evaluation.md)は全呼び出し・失敗・再試行を含む集計に使えますが、合成フィクスチャは実モデルの速度・品質・費用の証拠ではありません。

2026-09-10確認の通常API単価は、100万トークンあたりAstraが入力$10・出力$50、Lunaが入力$0.20・出力$1.20です。入力で50倍、出力で約42倍の差があります。したがって、Astraの大量探索・実装をLunaへ移す費用上の動機は強いです。一方、これはCodexの利用枠の消費比率や、Maxでの実際の出力量・実行時間を示す数字ではありません。[Astra](https://developers.openai.com/api/docs/models/gpt-6-astra)、[Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna)

最小化したいのは、受け入れ条件を満たすまでの総コストと時間です。総トークン、Astraトークン、Codex使用量、API費用を分けて記録します。並列化による総トークン増を、トークン削減として扱いません。

## 役割の分割

| 役割 | モデル・推論 | 担当 | 起動条件・権限 |
| --- | --- | --- | --- |
| Guildmaster | Astra・ユーザー指定 | 要件、依存関係、担当分割、難しい判断、統合、最終受け入れ | メイン1体。小さな作業は直接完了 |
| Scholar | Luna Max | 対象コード・仕様・資料の探索、影響範囲、仮説の反証 | 必要な未確認事項ごとに担当を分ける。読み取り専用 |
| Adventurer | Luna Max | 明確な受け入れ条件を持つ変更と局所テスト | 担当ファイルと共有資源を指定。workspace-write |
| Verifier（追加） | Luna Max | 要件から独立に検証項目を作り、受け入れテスト・境界ケースを確認 | テストの実行、指定されたテストファイル・生成物だけに書き込み。製品コードを修正しない |
| Sentinel（追加） | Luna Max | 通常の差分レビュー、仕様違反、回帰、検証漏れの指摘 | 実装者とは独立した読み取り専用の担当 |
| Inquisitor | Astra xhigh | 重大なリスクと重要な未解決事項の独立レビュー | 既存の重大リスク条件を維持。読み取り専用 |

カスタムエージェントの種類と、起動する人数を分けて考えます。4種類のLunaを定義しても、毎回4体を起動する必要はありません。同じ種類を複数起動し、別々の担当範囲を渡せます。

Scholarをコード用・Web用に恒久分割することや、言語別・画面別の役を増やすことは初期導入には含めません。調査の対象、観点、必要なSkillを短い依頼で選べば足りるためです。ツールや権限が明確に異なり、繰り返し使う用途が確認できた時に追加します。

Verifierは実装者の説明に追従せず、ユーザーの受け入れ条件と観測できる振る舞いから検証します。Sentinelは差分を読み、テストでは見落としやすい論理・互換性を確認します。小変更はAdventurerの局所テストとRootの確認だけで完了し、中程度の変更では不足する証拠に応じてVerifierかSentinelを選びます。Inquisitorを使う変更では、同じ観点のSentinelレビューを重ねません。

`sandbox_mode`は担当パス単位の書き込み制限ではなく、親の実行時設定にも左右されます。Verifierの「テストだけ」、Adventurerの「担当ファイルだけ」は委譲上の契約であり、OSが強制する隔離とは区別します。必要な隔離は利用可能なサンドボックスや明示したworktreeで行います。

## 人数を決める規則

| 作業 | 同時稼働の目安 | 分担例 |
| --- | --- | --- |
| 短い回答・自明な修正 | 子0〜1体 | Root直接、またはAdventurer 1体 |
| 通常の変更 | 子2〜4体 | 独立した調査と実装、完成した範囲から必要な検証 |
| 複数の独立した変更 | 子4〜6体 | 実装2〜3体と、別範囲の調査・検証 |
| 広いコード探索・資料比較・独立レビュー | 子5〜8体 | モジュール・資料・失敗仮説を重複なく分担 |
| 設計が未確定・変更が密結合 | 子1〜2体で開始 | Astraが共有仕様を決めてから拡大 |

実際の起動数は、設定枠、ホストが公開する空き枠、今着手できる独立タスク数、CPU・メモリ・外部APIなどの実行余力の最小値で決めます。共有チェックアウトへの同時書き込みは初期方針として最大3体とし、残りを独立した読み取りや検証に使います。この3体も上限であり、同じファイルやDBなどに触る担当は並べません。

実運用の拡大は4→6→8と段階的に行い、各段階で実機の起動・枠の解放と、未使用タスクでの品質・所要時間・使用量を確認します。設定上の上限8と、確認済みの運用人数を混同しません。

追加するのは「入力がそろっている」「担当と完了条件が独立している」「他の担当の完了待ちを減らす」の三条件を満たす仕事がある時です。競合、重複調査、再試行、API制限、テスト環境の競合、Rootの結果処理待ちが目立ったら新規起動を止め、担当をまとめます。同じ条件でLunaを再実行し続けず、最初の失敗で情報・分割を見直し、同じ原因で再び失敗したらAstraが引き取るか問題を分割し直します。

現セッションが公開する枠はメインを含め4体、子は最大3体です。設定ファイルを8にしても、この実行中セッションの枠が増えるとは扱いません。導入先への同期後、新しいセッションで有効な設定と実際の並列起動を確認します。

公式の上限は「同時に開いている子タスク」の上限です。完了と枠の解放を同一視しません。ネイティブの終了操作があるホストでは不要な子を閉じ、ないホストでは関連する継続作業に既存担当を再利用します。独立レビュー用の担当を実装者の再利用で代用しません。重大リスクがある場合は最初からInquisitor用の空き枠を確保します。[公式の子タスク上限](https://learn.chatgpt.com/docs/config-file/config-reference)

## 作業の流れと情報量

1. Astraが必要な最小範囲を確認し、目的、受け入れ条件、共有インターフェース、依存関係、担当パスを決めます。広い探索が必要なら、最初にScholarへ対象の地図を作らせます。
2. 着手可能な範囲をLunaへ渡します。Lunaは子を起動せず、Astraが直接調整します。担当ごとの長い計画書や常駐の中間管理役は作りません。
3. 独立した枝は並行して進めます。ある枝の編集が完了したら、その枝の検証を始められます。共有ファイルや共有テスト環境に依存する検証は、関連する編集が終わってから実行します。
4. Astraは要約と根拠を読み、矛盾する結果や重要な差分だけを追加確認します。要約だけで重大な変更を受け入れず、リスクに対応する原文・差分・実行結果を照合します。
5. 統合した状態に必要な確認を一度行い、変更がない限り同じ検証を繰り返しません。追加レビューや再試行は未解決の理由がある場合だけ行います。

委譲には新しい短いコンテキストを使い、対応するホストでは全会話のforkを避けます。目的、受け入れ条件、`guild_root`、`target_repo_root`、担当パス、権限、参照箇所、依存先だけを渡します。指示・安全制約を省略して短くすることはしません。目安は1件300〜800トークンですが、正確な委譲に必要なら超過できます。

返却は「結論または変更点／根拠の場所／実行した検証と結果／反証・未確認点／次に必要な判断」とし、通常300〜600トークンを目安にします。長いログや引用は参照先を返し、必要な部分だけAstraが読みます。独立した4体の結果が各500トークンなら、Rootが読む要約は約2,000トークンです。これは説明用の算例で、実測した節約量ではありません。

短い返答を要求しても内部の推論トークン上限にはなりません。Luna Maxの消費は、狭く十分な入力、明確な終了条件、重複排除、再試行の打ち切りで抑えます。機械的な一覧・差分・集計はまず検索、スクリプト、既存テストで処理し、判断が必要な部分をモデルに渡します。共有の前提は参照できる一か所に保ち、同じ長い資料を全担当に配りません。

最初の比較では現行のコンテキスト設定を維持して、役割分割と並列数の効果を測ります。その後の別実験で、Rootの自動コンパクションを20万、Lunaを8万にする候補を比較します。モデルの使用可能な窓は100万のままにし、長文を一度に扱うタスクは別条件に分けます。90万というしきい値自体は費用予算ではなく、コンパクションにも処理と情報損失の可能性があるため、単純に下げれば得とは決めません。[設定の意味](https://learn.chatgpt.com/docs/config-file/config-reference)

AstraのAPI料金は入力272K超で別倍率になります。API費用を評価する際にはこの境界、キャッシュ、推論を含む実際の使用量を考慮します。20万でのコンパクションを、その境界を絶対に越えない保証やCodex利用枠の節約保証にはしません。[Astraの料金条件](https://developers.openai.com/api/docs/models/gpt-6-astra)

## 精度を守る使い分け

多数のLunaに同じ問いをそのまま渡し、多数決で採用する運用にはしません。同じモデルが共通して誤る可能性があるため、実装・反例・実行テスト・仕様確認という異なる証拠を集めます。重要な仮説だけ、別担当に独立確認や反証を依頼します。

Astraが引き取る対象は、仕様の曖昧さ、複数領域の設計判断、Luna同士の証拠の衝突、繰り返す失敗、統合の難所です。既存の重大リスク条件を満たす場合は、さらに独立したInquisitorを使います。Luna側の自己申告の確信度や人数だけでエスカレーションを省略しません。

Rootがすべてのファイルを先に読み、実装を詳細に書き、それをLunaへ転記させる分担は費用削減に向きません。Rootは解くべき問題と受け入れ条件を決め、局所的な調査・実装・検証の思考をLunaへ渡します。

## 実装する場合の変更箇所

初期変更は設定と運用規則を中心にし、独自スケジューラー・キュー・台帳は追加しません。評価記録は既存の比較ツールを拡張して扱います。

設定差分の要点は次です。`[agents]`部分の候補であり、設定ファイル全体の置き換え用ではありません。

```toml
[agents]
enabled = true
max_concurrent_threads_per_session = 8
default_subagent_model = "gpt-5.6-luna"
default_subagent_reasoning_effort = "max"
```

各Lunaのカスタム定義にも`model = "gpt-5.6-luna"`と`model_reasoning_effort = "max"`を明記し、`[agents] enabled = false`を維持します。カスタム定義のモデル・推論設定が優先されるため、既定値だけに頼りません。[公式の設定優先順位](https://learn.chatgpt.com/docs/agent-configuration/subagents)

| 変更箇所 | 内容 |
| --- | --- |
| `template/.codex/config.toml` | サブエージェント上限8。Luna Maxの既定値維持 |
| `template/.codex/agents/` | VerifierとSentinelを追加。既存役の責務と返却形式を短く整合 |
| `template/AGENTS.md` | 可変人数、担当範囲、検証開始条件、結果の要約、再試行、枠の確保を規定 |
| `scripts/validation/basic.py` | 3役・上限3の固定検査を更新。全LunaのMaxと子起動禁止を検査 |
| `scripts/check_codex_parent.py`と関連テスト | 新役と有効な上限、明示したモデル・推論の観測を追加 |
| `tests/test_parent_install.py` | 旧3役からの更新、追加定義、独自設定と子リポジトリの保持を確認 |
| `scripts/model_selection_eval.py`・マニフェスト・フィクスチャ | 下記の実行プロファイルを区別できるよう拡張 |
| README・運用文書 | 役割数、可変人数、導入先の同期、新セッションでの確認を更新 |

導入先の独自設定は既存インストーラーの所有権ルールで保持し、配布元の変更だけで有効化したとは扱いません。Git安全規則と親・子の境界は維持します。

## 比較と採用の条件

同じ受け入れ条件、Root推論レベル、コンテキスト条件で比較します。まず現行構成と同じ上限3のまま役割分割を検証し、その後に上限4・8を比較すれば、どの変更が効いたかを分けて判断できます。

| 比較条件 | 目的 |
| --- | --- |
| Astraのみ | 単独実行の費用・精度・時間の基準 |
| 現行のAstra＋Luna、上限3 | 現在の運用の基準 |
| 提案する役割分割、上限3 | 人数を変えず役割・引き継ぎの効果を確認 |
| 同じ役割分割、上限4・8 | 並列化の効果と競合・統合費用を確認 |

既存ツールにはRoot／worker／reviewの区分があります。LunaのVerifierとSentinelはモデル会計上はworkerとし、重大リスクのAstra reviewと区別します。実行プロファイル、カスタム役名、観測した開始・終了時刻を追加し、プロファイル別集計と実並列数を確認できるようにします。現状のツールは2戦略を固定し、同じtask/strategyの重複を拒否するため、設定だけ変えて全条件を同じJSONLへ入れることはできません。再実行IDとプロファイルを検証・集計・重複判定に含める必要があります。

評価対象は、自明な変更、単一モジュール変更、複数モジュール変更、探索中心、重大リスクに分けます。パイロットで手順を確認した後、未使用のタスクを独立に評価します。各実行は新しいコンテキストとクリーンなチェックアウトで始め、順番・キャッシュ・API混雑の影響を記録します。

現行マニフェストは4タスクなので、広い用途での最適人数を決めるには不足しています。タスク群を増やし、同一条件の複数回実行も区別して記録します。役割の独立性、競合や待ち時間、レビューが実際に捕捉した不具合も確認し、単に「全員が完了した」を品質の証拠にしません。

採用判断では、受け入れ合格率と重大な見落としを先に確認し、全再試行・失敗・中断を含む総トークン、Astraトークン、実経過時間、Codex使用量、API費用を比較します。並列担当の実行時間を足し合わせてタスクの所要時間にしません。取得できない値はunknownのまま扱います。

品質を保ちながら総トークンも減る構成を優先します。総トークンが増えて費用や時間が改善した場合は、その交換条件を明示し、トークン削減の達成とは報告しません。小変更には直接実行、中変更には少数、大きな独立作業には多並列というように、作業群ごとに採用人数を選びます。最大8を一律の既定稼働数にはしません。

実装はこの設計判断を基にしています。実モデルの比較結果や8体並列の性能を合成フィクスチャから主張しません。検証・有効化の観測と限界は[親配置](parent-layout.md)に分けて記録します。
